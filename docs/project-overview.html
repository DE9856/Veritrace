Veritrace

Hallucination-Aware Information Assistant

An agentic assistant that answers questions from a document knowledge base and labels every claim in its answer as high-confidence, inferred, or potentially hallucinated, with a score and the evidence behind it.

Q: When did Chandrayaan-3 land, and what did the rover find? answer confidence 0.66 · 2 high · 1 inferred · 1 flagged

The Vikram lander touched down near the lunar south pole on 23 August 2023.[S1] The Pragyan rover confirmed sulphur in the surface near the landing site.[S2] This suggests the south polar surface chemistry differs from the equatorial sites sampled by earlier missions. The rover also detected water ice inside a crater close to the landing site.

Example output. Select a highlighted sentence to see the claim-level breakdown.

Problem

Language models write false statements in the same fluent, confident tone as true ones. The reader has no way to tell which parts of an answer are backed by evidence, which are reasonable deductions, and which are made up.

Goal

Build an assistant that checks its own answers before showing them. It breaks each answer into individual factual claims, verifies each claim against retrieved source passages and against its own repeated samples, and returns the answer with a visible confidence level for every sentence.

Scope

Questions are answered over a knowledge base of documents the user uploads (PDF, TXT, Markdown). Anything the knowledge base cannot support is labelled as unsupported rather than silently trusted. The system runs on free local models during development and switches to the Gemini API for the final version.

Confidence labels

Each atomic claim gets a score from 0 to 1 and one of three labels. A sentence takes the label of its weakest claim, and the answer as a whole gets a weighted average.

High confidence

score ≥ 0.75

The claim is directly stated in at least one retrieved source passage and the model gives the same claim consistently across samples.

NLI verdict: entailment. Shown with a citation to the source chunk.

Inferred

0.45 – 0.75

No single passage states the claim, but it follows logically from several supported facts taken together. Reasoning, summaries and comparisons usually land here.

NLI verdict: neutral, and the inference judge rules it derivable from the evidence.

Potentially hallucinated

score < 0.45, or contradicted

The sources contradict the claim, or nothing in the knowledge base supports it and the model's own samples disagree about it.

NLI verdict: contradiction, or neutral with no support. Shown with a warning and the reason.

Features

  • Document knowledge baseUpload PDFs and text files. They are parsed, chunked, embedded and indexed in ChromaDB.
  • Grounded answers with citationsAnswers cite the source chunks they rely on, as [S1] style markers that open the original passage.
  • Claim-level verificationEvery answer is split into atomic claims, and each claim is checked separately against the evidence.
  • Three-tier highlightingGreen, amber and red highlights per sentence, with a 0–100 score and an overall answer confidence.
  • Evidence inspectorClick a sentence to see its claims, the NLI verdict, the consistency score, and the passage used to check it.
  • Self-consistency checkThe model answers the same question several more times, and claims that change between samples lose confidence.
  • Agentic re-retrievalIf the first retrieval finds weak evidence, the agent rewrites the query and searches again before answering.
  • Safer answer rewriteAn optional mode that rewrites the answer to remove or hedge flagged claims, shown next to the original.
  • Live progressThe UI streams each agent step (retrieving, verifying, scoring) as it happens over Server-Sent Events.
  • Swappable model backendOne setting switches between local Ollama models and the Gemini API without code changes.

System architecture

Three layers: a Next.js frontend, a FastAPI backend that hosts the LangGraph agent, and the model and data services the agent calls. Ingestion runs as a separate path that fills the vector store.

Agent pipeline

The agent is a LangGraph StateGraph. Each node reads and updates one shared state object (query, evidence, draft answer, claims, scores). Conditional edges handle the retry loop and the optional revision step, and this is what makes the system agentic rather than a fixed chain.

  1. Analyze query LLM

    Classifies the question (factual, comparison, open-ended) and rewrites it into one to three search queries suited to the knowledge base.

  2. Retrieve evidence ChromaDB

    Runs a vector search for each query, merges the results, removes duplicates and keeps the top-k chunks (k = 6), labelled S1…S6.

  3. Evidence sufficient? Conditional edge

    If the best similarity score is below a threshold, the agent loops back and rewrites the query, at most twice. If evidence is still weak, it continues but marks the answer as low-coverage so most claims will be flagged.

  4. Generate answer LLM

    Writes the answer using only the numbered evidence, cites chunks inline, and tags each sentence with its own confidence (HIGH, INFERRED, UNSURE). That self-label is one of the scoring signals.

  5. Extract claims LLM · JSON

    Breaks each sentence into atomic, standalone claims and returns structured JSON that maps each claim to its sentence index.

  6. Verify with NLI DeBERTa

    Each claim is the hypothesis and each evidence chunk is the premise. The model returns entailment, neutral and contradiction probabilities. The strongest entailment and contradiction across chunks are kept, along with the chunk that produced them.

  7. Judge inference LLM

    Only for claims that came back neutral. A judge prompt is given all the evidence together and asked whether the claim is a reasonable deduction from it. This step separates inferred claims from unsupported ones.

  8. Consistency check LLM + NLI

    Samples N more answers at a higher temperature (N = 3 locally, 2 on Gemini because of free-tier limits). For each claim, it measures the fraction of samples that entail it, following the SelfCheckGPT approach.

  9. Score and label Deterministic

    Combines the signals into a score per claim, applies the override rules, assigns labels, and rolls the results up to sentences and to the whole answer.

  10. Revise LLM · optional

    If the user turns on safe mode and any claim is flagged, this step rewrites the answer to remove or hedge flagged claims. Both versions are returned.

Confidence scoring

The score combines several independent signals, so the model's opinion of its own answer is never the only input. Claim verification against evidence carries the most weight.

score = 0.55·E + 0.20·C + 0.15·R + 0.10·L
  • E: highest NLI entailment probability across evidence chunks
  • C: self-consistency, the fraction of resampled answers that support the claim
  • R: retrieval relevance of the best supporting chunk (cosine similarity, normalised)
  • L: the generator's own label (HIGH = 1.0, INFERRED = 0.5, UNSURE = 0.2)

Override rules

  • Contradiction probability above 0.7 sets the label to hallucinated, whatever the score.
  • A neutral NLI verdict that the inference judge rules derivable is raised to at least inferred.
  • An entailment above 0.85 with consistency of at least 0.67 is high.

Roll-up

A sentence takes the label of its weakest claim. The answer's confidence is the average of its claim scores, weighted by claim length, and is shown next to a count of claims in each tier. The weights and thresholds live in config.yaml and are tuned against a small hand-labelled set of question and answer pairs.

How everything connects

Ingestion flow

  1. The user drops a PDF into the upload panel in the UI.
  2. Next.js sends it to POST /api/documents as multipart form data.
  3. FastAPI saves the file, PyMuPDF extracts text page by page, and pysbd splits it into sentences.
  4. Sentences are grouped into chunks of about 400 tokens with a 60-token overlap, each tagged with document id, page and chunk index.
  5. bge-small embeds the chunks, which are stored in a ChromaDB collection.
  6. The document record is saved to SQLite and the UI list refreshes.

Question flow

  1. The user asks a question. Next.js opens an SSE stream to POST /api/chat.
  2. FastAPI creates the initial agent state and runs the LangGraph graph.
  3. As each node finishes, the backend sends a status event and the UI shows the current step.
  4. The draft answer streams in as token events, displayed without highlights at first.
  5. After scoring, a verdict event carries every sentence, claim, score and evidence reference.
  6. The UI applies the highlights. Clicking a sentence opens the evidence inspector, and clicking a citation opens the source chunk.

Model strategy: local first, Gemini at the end

All LLM calls go through one small interface, so moving from Ollama to Gemini only changes an environment variable.

class LLMProvider(Protocol):
    async def generate(self, prompt: str, *, temperature: float = 0.2) -> str: ...
    async def generate_json(self, prompt: str, schema: type[BaseModel]) -> BaseModel: ...
    async def sample(self, prompt: str, n: int, temperature: float = 0.8) -> list[str]: ...

# providers/ollama.py   -> uses format="json" for structured output
# providers/gemini.py   -> uses response_schema for structured output
# providers/factory.py  -> picks one from LLM_PROVIDER=ollama|gemini|groq

Staying inside the free tier

  • Extract claims for the whole answer in one call, and run the inference judge on a batch of claims at once, rather than one call per claim.
  • NLI runs locally on DeBERTa, so the most frequent check costs no API calls.
  • Make the number of consistency samples configurable (3 locally, 2 on Gemini), and add a retry with backoff for rate-limit errors.
  • Cache results by question and document set, so repeated questions during development don't use up quota.
  • If Gemini returns a rate-limit error, the factory switches to the fallback provider.

Prompts live in versioned files under prompts/. When the backend switches to Gemini, only the prompts that need adjusting change; the graph code stays the same.

Deployment

Deployment happens after the switch to Gemini, so the hosted backend doesn't need to run an LLM. It still runs the embedding model and the NLI model on CPU, which need about 1.5 GB of RAM in total.

PartHostNotes
FrontendVercel (free)Next.js deploys from the Git repository. The backend URL is set through NEXT_PUBLIC_API_URL.
BackendHugging Face Spaces, Docker SDK (free CPU tier)Free tier has enough RAM for DeBERTa and bge, unlike the 512 MB free tiers elsewhere. The Gemini key is stored as a Space secret.
Vector dataChromaDB inside the SpaceFree Space storage is reset on restart, so sample documents are bundled and re-ingested on startup. User uploads last for the session.

For local development, docker compose runs the backend, frontend and Ollama together.

Build roadmap

Each phase leaves a working system, so there is always something to show.

  1. Phase 1
    Foundations and RAGFastAPI skeleton, Ollama provider, ingestion pipeline, ChromaDB, and a plain grounded answer with citations.
  2. Phase 2
    Claim verificationClaim extraction prompt with JSON output, DeBERTa NLI verification, and the first labels using the NLI verdict only.
  3. Phase 3
    Full scoringSelf-labels, consistency sampling, the inference judge, the weighted score, override rules and roll-up. Tune thresholds on a small labelled set.
  4. Phase 4
    Agentic graphMove the pipeline into LangGraph with the retry loop, the sufficiency check and the optional revise node. Stream the node status over SSE.
  5. Phase 5
    FrontendChat UI, highlighted answers, evidence inspector, citation viewer, upload panel and the live agent-step indicator.
  6. Phase 6
    Gemini and deploymentGemini provider and prompt adjustments, rate-limit handling and fallback, Dockerfile, then deploy to Hugging Face Spaces and Vercel.

Design decisions

DecisionChosenAlternatives and why not
Grounding sourceUploaded document knowledge baseLive web search needs paid APIs and is noisy. Self-checking alone cannot confirm that a claim is supported.
Detection methodEnsemble led by claim-level NLI, plus consistency and self-labelsLogprobs are unavailable on Gemini and poorly calibrated. Self-labels alone mean the model grades its own work.
Verifier modelSeparate DeBERTa NLI modelUsing the generator as its own judge shares its blind spots. A separate, smaller model gives an independent check at no API cost.
GranularityVerify claims, display sentencesSentence-only checking misses a false fact mixed with true ones. Showing claims only is cluttered.
OrchestrationLangGraph state graphA plain function chain cannot easily loop or branch. A free-form ReAct agent is less predictable for a verification pipeline.
ModelsOllama during development, Gemini for the final versionStarting on Gemini would use up the free quota during development. Staying local would weaken extraction and judging quality.

Limitations and future scope

Known limitations

  • Claims outside the uploaded documents are labelled unsupported even when they are true.
  • NLI models struggle with numbers, dates and negation across long passages.
  • Consistency sampling adds latency and API calls.
  • The score weights are set by hand and only roughly calibrated.
  • The knowledge base is English-only.

Future scope

  • Web search as a second evidence source when the knowledge base has no coverage.
  • A learned calibration model, such as logistic regression over the signals, in place of fixed weights.
  • A cross-encoder reranker to improve evidence quality.
  • Multilingual support using Sarvam models for Indian languages.
  • User feedback on labels, stored to improve the thresholds over time.
